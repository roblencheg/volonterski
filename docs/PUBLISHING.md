# Публикация

## Формат

Создать src/content/articles/<id>.md:

```yaml
---
title: "Заголовок"
description: "Короткий результат и польза материала."
date: 2026-10-29
tags: ["Инструкции", "ИИ"]
draft: false
attachments:
  - name: "Архив проекта"
    url: "/files/<id>/project.zip"
    size: "120 КБ"
---
```

Статьи о собственных проектах пользователя ведутся от первого лица автора. Не описывать их как чужие проекты и не приписывать автору неподтверждённый опыт.

Далее обычный Markdown. Допустимы заголовки ##, таблицы, изображения, блоки кода с языком. Для непроверенных действий явно указывать статус. published URL: https://volonterski.ru/articles/<id>/.

Файлы лежат в public/files/<id>/. Ссылки в тексте начинаются с /files/<id>/. Вложения и статья коммитятся вместе. Весь репозиторий публичен, включая историю и draft: true. Закрытые черновики держать вне репозитория.

Обновление: оставить имя файла/date, добавить updated: YYYY-MM-DD. Удаление: удалить статью и неиспользуемые вложения; учесть ранее выданные ссылки.

## Публикация из другого чата

Одноразово добавить в инструкции проекта ChatGPT:

> Когда я говорю «пиши статью на сайт», публикуй результат текущего обсуждения в GitHub roblencheg/volonterski. Сначала прочитай AGENTS.md и docs/PUBLISHING.md в этом репозитории. Используй доступный инструмент записи GitHub, добавь статью и материалы одним коммитом в main, проверь сборку и верни ссылку. Если инструмента записи нет, сообщи об этом прямо. Не называй материал опубликованным до успешного деплоя.

Это инструкция, а не установленный глобальный навык. Она работает только в окружении, где подключён GitHub с правами записи в данный репозиторий. Отдельный publishing API или LLM API для этой схемы не нужен.

## Проверка

npm ci
npm run build
npm run verify

CI делает те же проверки. Pull request только проверяется, main публикуется. Тяжёлые файлы не раздувать в Git: согласовать отдельное хранилище/Release и правило постоянных ссылок.

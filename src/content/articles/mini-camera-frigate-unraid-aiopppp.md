У меня лежала старая мини-камера: при включении она создавала собственную точку Wi-Fi, а для просмотра требовала приложение. Я подключил её к домашней сети, затем получил изображение в Frigate на Unraid через небольшой программный мост.

Рабочая схема использует **aiopppp 0.2.3** и встроенный в Frigate **go2rtc**. Приложение понадобилось для первоначальной настройки Wi-Fi. После запуска моста телефон и компьютер Windows больше не участвуют в передаче видео.

## Что именно удалось подключить

Камера создавала сеть с префиксом **DGOE** и работала с **HDWiFiCamPro**. В её журнале определилась прошивка `HQ6_IPC_20230224 14:34:36`. Это описание проверенного экземпляра, а не гарантия совместимости всех внешне похожих мини-камер.

Быстрая проверка портов показала открытый TCP `5007`. На проверенных портах `80`, `443`, `554`, `8554`, `8080`, `8081` и `8899` ответа не было. Такой результат не доказывает полного отсутствия RTSP: проверялись только выбранные порты. Но рабочим способом для моей камеры оказался протокол **PPPP** через библиотеку aiopppp.

Результат этого эксперимента — изображение в Frigate. Запись, распознавание объектов, звук и длительную устойчивость работы я этим тестом не подтверждал. Отдельное появление камеры в Home Assistant также не входило в финальную проверку.

## Сначала проверил камеру на Windows

Через HDWiFiCamPro я добавил камеру в домашнюю Wi-Fi-сеть и посмотрел выданный ей IP. Для постоянной установки стоит закрепить этот адрес в DHCP роутера.

Далее на компьютере в той же сети создал отдельное Python-окружение. Команды выполняются по очереди в PowerShell; нужен установленный Python с командой `py`:

```powershell
py -m venv "$env:USERPROFILE\camera-test"
```

```powershell
& "$env:USERPROFILE\camera-test\Scripts\python.exe" -m pip install aiopppp==0.2.3
```

```powershell
& "$env:USERPROFILE\camera-test\Scripts\python.exe" -m aiopppp -u admin -p "CAMERA_PASSWORD"
```

Здесь и далее `CAMERA_PASSWORD` нужно заменить паролем самой камеры, а не домашней Wi-Fi-сети. Логин `admin` тоже следует сверить со своим устройством. Мобильное приложение перед проверкой я закрыл.

После запуска открыл `http://localhost:4000`. Камера обнаружилась, появилось видео. Это был главный тест совместимости: сходство корпуса или префикса Wi-Fi само по себе ничего не гарантирует.

Веб-сервер aiopppp отдаёт MJPEG по пути:

```text
http://АДРЕС_МОСТА:4000/UID_КАМЕРЫ/v
```

UID берётся из списка обнаруженных устройств. В примерах ниже я использую вымышленный `DGOE-123456-ABCDE`, а IP `192.168.1.50` — пример адреса камеры. Оба значения нужно заменить своими.

## Почему первый запуск на Unraid не заработал в Frigate

Сам мост успешно получал видео в режиме Docker `host`. Страница на порту `4000` открывалась с компьютера, но Frigate находился в сети `br0` и не мог обратиться к адресу хоста Unraid:

```text
Connection to tcp://UNRAID_IP:4000 failed: No route to host
```

Я попробовал перенести мост в обычную Docker-сеть `bridge` и добавить общую внутреннюю сеть между ним и Frigate. HTTP-связь появилась: запрос из Frigate возвращал `200`. Однако камера перестала обнаруживаться, а запрос видеопотока возвращал `404`.

В журнале был запуск поиска на UDP `32108`, но не было найденного устройства. Точную причину отсутствия ответа в этой конфигурации я не установил. Поэтому вывод здесь узкий: **в моей установке этот вариант сети не сработал**, а не «PPPP никогда не работает через NAT».

Рабочим решением стал режим **`--network container:frigate`**. Мост использует сетевое пространство Frigate, получает доступ к домашней сети через его `br0`, а сам Frigate обращается к мосту по `127.0.0.1:4000`.

## Рабочая установка на Unraid

Перед переносом нужно остановить тестовый сервер на Windows сочетанием `Ctrl+C` и закрыть страницу с видео. Дальнейшие команды выполняются в терминале Unraid. В примере существующий контейнер Frigate называется `frigate`.

### 1. Собрать образ моста

Команда создаёт локальный образ на базе Python 3.12 и фиксирует версию aiopppp:

```bash
printf '%s\n' 'FROM python:3.12-slim' 'RUN pip install --no-cache-dir aiopppp==0.2.3' 'ENTRYPOINT ["python", "-m", "aiopppp"]' | docker build -t local/aiopppp:0.2.3 -
```

### 2. Проверить свободный порт

Frigate должен быть запущен. Проверка временно занимает и сразу освобождает порт `4000` в его сетевом пространстве:

```bash
docker exec frigate python3 -c "import socket; s=socket.socket(); s.bind(('0.0.0.0',4000)); print('Port 4000 free'); s.close()"
```

Если вместо `Port 4000 free` получена ошибка занятости порта, продолжать с этим портом нельзя: сначала нужно определить, какой сервис его использует.

### 3. Запустить контейнер

```bash
docker run -d --name mini-camera-bridge --network container:frigate --restart unless-stopped --log-opt max-size=10m --log-opt max-file=3 local/aiopppp:0.2.3 -a 192.168.1.50 -u admin -p 'CAMERA_PASSWORD'
```

Параметр `-a` задаёт адрес камеры. Публикация порта через `-p 4000:4000` здесь не нужна и не поддерживается режимом `container:`.

Команда рассчитана на новую установку. Если контейнер с именем `mini-camera-bridge` уже существует, сначала разберитесь с ним: повторный `docker run` не обновляет существующий контейнер.

Пароль в такой команде доступен администратору через настройки контейнера и может остаться в истории терминала. Не публикуйте её с реальным паролем.

### 4. Убедиться, что найдена именно камера

Примерно через 15 секунд:

```bash
docker logs --tail 40 mini-camera-bridge
```

Проверка списка устройств из Frigate:

```bash
docker exec frigate python3 -c "import urllib.request,re; s=urllib.request.urlopen('http://127.0.0.1:4000/',timeout=5).read().decode(); print('Camera IDs:',re.findall(r'<h2>(.*?)</h2>',s))"
```

Ожидаемый результат содержит реальный UID:

```text
Camera IDs: ['DGOE-123456-ABCDE']
```

Если список пуст, настройка YAML ещё не решит проблему: веб-сервер доступен, но сессии камеры нет.

## Конфигурация Frigate

Мост отдаёт MJPEG. Для дальнейшей работы go2rtc преобразует его в H.264 и предоставляет локальный RTSP-поток. Это программное кодирование, поэтому нагрузка на процессор выше, чем при получении готового H.264 напрямую с камеры.

В существующий конфиг нужно добавить записи внутрь разделов `go2rtc.streams` и `cameras`, а не создавать дублирующиеся корневые ключи:

```yaml
go2rtc:
  streams:
    mini_camera:
      - "ffmpeg:http://127.0.0.1:4000/DGOE-123456-ABCDE/v#video=h264"

cameras:
  mini_camera:
    enabled: true
    ffmpeg:
      inputs:
        - path: rtsp://127.0.0.1:8554/mini_camera
          input_args: preset-rtsp-restream
          roles:
            - detect
    detect:
      enabled: false
      fps: 5
    record:
      enabled: false
```

Это фрагмент для уже настроенного Frigate. UID в URL нужно заменить значением из предыдущей проверки. Распознавание объектов и запись намеренно выключены: сначала я проверял получение изображения. `fps: 5` относится к обработке в Frigate, а не задаёт частоту исходного видео камеры.

После проверки конфигурации и перезапуска Frigate я перезапустил мост:

```bash
docker restart mini-camera-bridge
```

После этого видео появилось в Frigate.

## Как читать ошибки

| Симптом | Что проверять |
| --- | --- |
| `No route to host` | Сетевой путь от Frigate до моста. Это ещё не ошибка декодирования видео. |
| Главная страница отвечает `200`, поток — `404` | Найдена ли камера и совпадает ли UID в URL. В моём случае список устройств был пуст. |
| `NotImplementedError` после изменения параметров | Метод управления не реализован для выбранной сессии. У меня это происходило при вызове `set-video-param`. |
| `Connection reset` после закрытия страницы | Клиент разорвал HTTP-соединение. Само по себе это не доказывает неисправность камеры. |

Кнопки настройки в тестовом интерфейсе не означают, что все функции поддерживаются конкретной камерой. Управление разрешением и другими параметрами я не стал включать в рабочую схему.

Также я закрываю прямой просмотр через порт `4000`, когда поток забирает Frigate. В этой реализации HTTP-сервера клиенты читают кадры из общей очереди и могут конкурировать за них. Для нескольких зрителей лучше использовать раздачу уже через go2rtc/Frigate.

## Ограничения постоянной эксплуатации

**Мост зависит от контейнера Frigate.** Режим `container:frigate` разделяет его сетевое пространство. После пересоздания Frigate при обновлении нужно пересоздать и мост, выполнив остановку, удаление именно контейнера моста и повторный запуск командой выше. Образ удалять не требуется. При обычном перезапуске сначала стоит перезапустить мост и проверить список камер.

Политика `--restart unless-stopped` сама по себе не гарантирует правильного порядка запуска после перезагрузки Unraid и не проверяет наличие кадров. Автоматическое восстановление после всех видов сбоев в этом эксперименте не проверено.

**Тестовый веб-сервер не стоит выставлять в интернет.** В проверенном коде он слушает `0.0.0.0:4000` и не содержит HTTP-аутентификации. При совместной сети он доступен и по LAN-адресу Frigate, если это допускают сетевые правила. Через него доступны не только кадры, но и команды управления.

**Локальное получение видео не доказывает отключения облака камеры.** Приложение больше не требуется для просмотра, но обращения самой камеры к серверам производителя здесь не исследовались. Проверку работы с запрещённым доступом камеры в интернет нужно проводить отдельно.

Если Frigate уже интегрирован с Home Assistant, следующий шаг — проверить появление новой камеры в этой интеграции. Подтверждённый результат описанной настройки заканчивается на рабочем изображении в Frigate.
